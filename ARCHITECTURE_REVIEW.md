# Architecture Review
Generated: 2026-08-30T20:25:20.569Z
Score: 60/100

## Summary
The codebase shows strong per-file craftsmanship (consistent doc-comments, guarded SDK calls, a real shared component library for cards/heroes/skeletons), but it has accumulated cross-file architecture debt: two colliding type systems (contract.ts vs lib/types.ts) define same-named types with different shapes, an entire leaderboard-generation module is disconnected from the page that actually needs it, and several small imperative patterns (haptics, price-fallback, disclaimer text) are copy-pasted instead of centralized despite equivalent shared components already existing. No true circular imports were found. Overall the foundation is sound but needs a cleanup pass to remove stale scaffold types, wire up (or delete) unused modules, and enforce use of the 'pre-built, do not reimplement' components its own comments call for.

## Issues
### Critical
- [naming] Two unrelated types are both named `RouteState` and are both actively imported/used under that name: contract.ts defines `{ currentScreen, tradePreview }` (used by App.tsx for screen-name routing), while lib/types.ts defines a totally different route-path-keyed map `{ '/': ..., '/portfolio': ..., ... }` (used by Portfolio.tsx and others for `location.state` typing). This is a genuine footgun for anyone importing `RouteState` from the 'wrong' module, and signals contract.ts and types.ts have diverged without reconciliation. — Files: src/lib/contract.ts, src/lib/types.ts, src/App.tsx, src/pages/Portfolio.tsx / Fix: Rename one of the two types (e.g. `ScreenRouteState` vs `PathRouteState`) or delete contract.ts's version if it's stale scaffold, and have all pages import the single canonical `RouteState` from lib/types.ts.
- [dead_code] src/lib/leaderboard.ts (132 lines: deterministic bot generation, getLeaderboardSeed, buildLeaderboard, clearLeaderboardSeedCache) defines its own `LeaderboardEntry` shape (id/nickname/totalAssetKrw/returnPct/streak) and is re-exported through lib/quiz.ts, but the actual Leaderboard.tsx page never imports from lib/leaderboard.ts — it calls `loadLeaderboardSeed()` from lib/storage.ts instead, consuming a different entry shape (userId/userName/score). The sophisticated bot-seeding logic appears to be entirely unwired dead code, and quiz.ts re-exporting an unrelated leaderboard module is a code-smell suggesting a half-finished refactor. — Files: src/lib/leaderboard.ts, src/lib/quiz.ts, src/pages/Leaderboard.tsx, src/lib/storage.ts / Fix: Determine which leaderboard data source is canonical (storage.ts's static seed or leaderboard.ts's generated bots), delete the other, and remove the leaderboard re-export from quiz.ts.

### Suggestions
- [duplication] Amount.tsx and CountUp.tsx implement essentially the same wrapper (inline-block span, nowrap, tabular-nums, Paragraph.Text with formatNumber+unit) — CountUp just adds an animation loop on top. — Files: src/components/Amount.tsx, src/components/CountUp.tsx / Fix: Factor the shared span/typography markup into an internal `NumberDisplay` primitive that both Amount and CountUp render, so the nowrap/tabular-nums contract only exists in one place.
- [dead_code] src/components/LoadingSkeletons.tsx (HeroSkeleton, ListSkeleton) overlaps in purpose with StateView.tsx's `LoadingState`, and none of the reviewed pages (Home, Market, Portfolio, Backtest, BacktestResult, Quiz, QuizResult, Leaderboard, Trade) import HeroSkeleton or ListSkeleton — only LoadingState/EmptyState from StateView.tsx are used. — Files: src/components/LoadingSkeletons.tsx, src/components/StateView.tsx / Fix: Confirm whether LoadingSkeletons is actually consumed anywhere; if not, delete it, or consolidate it with StateView.tsx's LoadingState so there is one loading-placeholder API.
- [structure] src/lib/navigation.ts (a 'lib' module) imports the `TabItem` type from src/components/FloatingTabBar.tsx (a component), inverting the usual dependency direction where components depend on lib, not vice versa. It isn't a cycle today only because FloatingTabBar.tsx doesn't import navigation.ts back, but the layering makes that an easy mistake to introduce later. — Files: src/lib/navigation.ts, src/components/FloatingTabBar.tsx / Fix: Move the `TabItem` type (and possibly MAIN_TAB_ITEMS) into lib/ or a dedicated types module so components import from lib, not the other way around.
- [consistency] Most domain state (account, positions, trades, streak) flows exclusively through AppStateContext with storage.ts as the only persistence gate, but Backtest.tsx reads/writes `presets` directly via `loadPresets()`/`savePresets()` from lib/storage.ts inside the component, bypassing the context and giving that one feature a different state-management pattern than the rest of the app. — Files: src/pages/Backtest.tsx, src/store/AppStateContext.tsx, src/lib/storage.ts / Fix: Either move presets into AppStateContext alongside the other domain state for a single consistent data-flow pattern, or explicitly document why presets are intentionally local/page-scoped.
